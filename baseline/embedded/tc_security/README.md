# Flight TC security receiver

This module is the embedded-C counterpart of the ground CCSDS TC protection
path. It implements two SPI-selected profiles with no optional-tag branch:

```text
TC primary header (5)
|| SPI (2)
|| IV_COUNTER (4)
|| AES-256-CTR or SM4-CTR ciphertext (N)
|| FECF (2)
```

The ordinary profile has no tag field. `TCSEC_OK` therefore means that the frame was decrypted,
passed structural/application validation, and had its replay state persisted.
It never means authenticated, verified, or trusted.

```text
TC primary header (5)
|| recovery SPI (2)
|| IV_COUNTER (4)
|| AES-256-GCM or SM4-GCM ciphertext (39 or 55)
|| TAG (16)
|| FECF (2)
```

Recovery plaintext is the one fixed root-recovery transaction. Its full tag
authenticates `primary || SPI || IV` as AAD and the transaction as ciphertext.
It is never released through the ordinary plaintext buffer.

## Interface

Callers configure up to three fixed AES-256 or SM4 key slots and four Security
Associations, then call `tcsec_receive` with one complete transfer frame. SPI
selects the SA profile and its bound suite. The
module hides frame-length/FECF validation, SPI lookup, CTR counter construction,
decryption, the 64-entry IV window, validation ordering, and atomic replay
commit behind that one receive interface.

`tcsec_context_t` is intentionally not internally synchronized. A flight task
must serialize calls for one context, which is also what makes replay check,
durable persistence, and in-memory commit one ordered receive transaction.

The platform supplies adapters only for profiles it configures:

- `validate_plaintext` applies command-format and mission-state checks. It runs
  before replay state changes.
- `persist_replay` atomically writes the new `(highest_iv, bitmap, seen)` state.
  The module releases no plaintext if persistence fails.
- `commit_recovery` atomically validates and commits the typed root transaction
  together with the supplied next Recovery replay state. It reports new,
  idempotently already-applied, rejected, or persistence-failed.

The CTR initial counter is:

```text
SA_NONCE_PREFIX (6) || SPI (2) || IV_COUNTER (4) || BLOCK_COUNTER (4)
```

`BLOCK_COUNTER` starts at zero and increments within the frame. Ground and
flight use the same big-endian construction.

## Embedded properties

- C11, no heap allocation, no global mutable state;
- fixed maximum 1024-byte TC frame;
- fixed AES-256/SM4 CTR ordinary suites and GCM recovery suites; no wire negotiation or plugin registry;
- exactly one SA per key slot, so rotation cannot accidentally reuse one key
  under a different SPI/prefix;
- key material and temporary AES state are explicitly zeroized;
- SPI and IV are parsed as big-endian values;
- replay state changes only after plaintext validation and durable persistence;
- AOS, transmit, JSON, databases, and ground administration concepts are absent;
- CMAC Counter KDF derives the three working slots from platform-held roots;
- recovery uses full-length GCM tags and an atomic platform persistence seam.

Because CTR has no authentication, the replay window is duplicate filtering,
not cryptographic anti-replay. An active attacker may still modify ciphertext,
SPI, IV, and FECF. The plaintext validator and command interlocks reduce random
failure propagation but do not create cryptographic integrity.

## Test

From `baseline/embedded/tc_security` on a host with a C11 compiler:

```sh
make test
```

The test runs AES-256-CTR and SM4 known-answer vectors, shared CMAC Counter KDF
vectors, then consumes ordinary CTR and recovery GCM frames generated by the Go
ground implementation. It checks replay rejection, FECF failure, full-tag
tamper rejection, strict three-slot configuration, and persistence failures.
